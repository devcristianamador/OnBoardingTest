## Context

This is a greenfield Angular application for managing bank branches at Davivienda. There is no existing frontend — the `frontend/` directory will host the new Angular project. The application uses PrimeNG for UI components, PrimeFlex for layout utilities, and stores data in-memory (no backend API). Testing uses Karma + Jasmine following Davivienda standards.

## Goals / Non-Goals

**Goals:**
- Scaffold a new Angular application with PrimeNG and PrimeFlex
- Implement a `Branch` model interface with `id`, `name`, and `address` fields
- Create a `BranchService` that stores branches in-memory and exposes CRUD methods
- Build a `BranchListComponent` using PrimeNG Table for displaying branches
- Build a `BranchFormComponent` using PrimeNG Dialog with a reactive form for create/edit
- Add delete confirmation via PrimeNG ConfirmDialog
- Achieve unit test coverage for both service and components

**Non-Goals:**
- Backend API integration or persistent storage
- Authentication or authorization
- Routing between multiple pages (single-page CRUD is sufficient)
- Internationalization (i18n)

## Decisions

### 1. In-Memory Storage via BehaviorSubject

**Decision**: Use a `BehaviorSubject<Branch[]>` in `BranchService` to hold branch data and expose it as an `Observable`.

**Rationale**: BehaviorSubject provides a reactive stream that components can subscribe to, ensuring the UI stays in sync with data changes. It's simple, testable, and follows Angular reactive patterns.

**Alternative considered**: Plain array property — rejected because it doesn't provide reactive updates to subscribers.

### 2. Component Architecture

**Decision**: Two components — `BranchListComponent` (table + toolbar) and `BranchFormComponent` (dialog form) — plus the `BranchService`.

**Rationale**: Separating list and form concerns keeps components focused and testable. The form component handles both create and edit via an input binding.

**Alternative considered**: Single component with inline form — rejected because it reduces testability and violates single-responsibility principle.

### 3. PrimeNG Table + Dialog Pattern

**Decision**: Use `p-table` for the list view, `p-dialog` for the form, and `p-confirmDialog` for delete confirmation.

**Rationale**: PrimeNG provides production-ready, accessible components. The Table + Dialog pattern is a standard PrimeNG CRUD pattern with built-in support for sorting, pagination, and responsive design.

### 4. Reactive Forms for Branch Form

**Decision**: Use Angular Reactive Forms (`FormGroup`, `FormControl`) with Validators for the branch create/edit form.

**Rationale**: Reactive forms provide explicit control over form state, validation, and testability. They are well-suited for forms that need programmatic manipulation (e.g., resetting on dialog open, patching values for edit).

### 5. Auto-Incrementing ID

**Decision**: Use a simple auto-incrementing numeric ID generated by the service.

**Rationale**: Sufficient for in-memory storage. No need for UUID complexity without a backend.

## Risks / Trade-offs

- **[Data loss on refresh]** → Expected behavior for in-memory storage. Out of scope for this feature; a future feature could add localStorage or API persistence.
- **[PrimeNG version compatibility]** → Use the latest PrimeNG version compatible with the installed Angular version. Verify during `ng add primeng`.
- **[No pagination for large datasets]** → PrimeNG Table supports pagination out of the box; can be enabled if branch count grows. For this demo, a simple table is sufficient.
